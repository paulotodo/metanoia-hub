## Overview

**Page Purpose:** Formulario para criar novo tenant + execucao da saga de provisionamento (database → Keycloak realm → admin user + convite). Paulo preenche 4 campos, toca "Criar", e acompanha o progresso da saga em tempo real via stepper visual.

**User Situation:** Segunda de manha. Paulo verificou no dashboard (09.2) que nao existe duplicata. Clicou "Novo Tenant". Precisa provisionar "Igreja Restauracao" e enviar convite ao admin designado. ≤5 minutos total.

**Success Criteria:** Em ≤2 minutos, Paulo preenche o formulario e a saga completa com sucesso. Convite enviado ao admin. Redirect para detalhe (09.4).

**Entry Points:**
- (1) "Novo Tenant" na 09.2

**Exit Points:**
- (1) Saga sucesso → redirect 09.4 (detalhe do tenant criado)
- (2) Cancel → volta 09.2
- (3) Saga falha → estado de erro com retry

**Route:** `/app/admin/super/tenants/novo` — rota protegida, guard `@Roles('super_admin')`.

## Technical Notes

- **Rendering:** CSR — rota protegida `/app/admin/super/tenants/novo`. Guard `@Roles('super_admin')`.
- **API:** POST `/api/v1/admin/super/tenants` → 202 (Accepted). Body: `{ name, slug, adminEmail, plan }`. Retorna `{ tenantId, status: "provisioning" }`.
- **Saga pattern (Story 3.1):**
  1. Create tenant record in database (status: `provisioning`)
  2. Create Keycloak realm with tenant config
  3. Create admin user in Keycloak + send invite email
  - Rollback: se step 2 falha, marca tenant como `provisioning_failed`. Se step 3 falha, Keycloak realm existe mas admin nao — retry apenas step 3.
- **Polling:** Frontend polls `GET /api/v1/admin/super/tenants/{id}/provision-status` a cada 2s. Response: `{ step: 1|2|3, status: "running"|"done"|"failed", error?: string }`.
- **Slug generation:** `slugify(name)` — remove acentos, lowercase, replace spaces with hyphens, remove special chars.
- **PrismaAdminService:** Saga usa connection pool sem RLS para criar tenant cross-tenant.
- **Domain event:** `tenant.provisioned` com `{ tenantId, plan, provisionedBy, sagaDurationMs }`.
