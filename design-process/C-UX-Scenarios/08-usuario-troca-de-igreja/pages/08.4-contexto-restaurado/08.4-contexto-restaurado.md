## Overview

**Page Purpose:** Confirmação implícita de que o contexto da igreja correta foi carregado. Não é uma tela nova — é o resultado do redirect pós-seleção (08.2) ou pós-switch (08.3). O ExperienceResolver lê o role do usuário no tenant selecionado e redireciona para a experiência consolidada com dados isolados.

**Why specified-light:** Não há UI nova. O redirect é o mesmo ExperienceResolver usado em 01.1, 03.1, 06.3, 07.5. A confirmação é implícita: Marcos vê o radar com o nome da igreja certa no header.

---

## Redirect Flow

```
[08.2 ou 08.3 — tenant selecionado]
    │
    ├── Cookie: tenant_id = {selected_tenant}
    ├── RequestContext: tenant_id via AsyncLocalStorage
    │
    └── ExperienceResolver
        │
        ├── Role neste tenant: Líder → /app/gestao/radar (01.2)
        ├── Role neste tenant: Admin Tenant → /app/admin/ (03.2)
        ├── Role neste tenant: Participante → /app/consumo/grupos (06.4)
        └── Role neste tenant: Super Admin → /app/ops/
```

**Design decision:** O redirect resolve por role **no tenant selecionado**, não por role global. Marcos pode ser Líder na Vida Nova e Participante na Graça Plena — o ExperienceResolver redireciona para experiências diferentes conforme o tenant.

---

## Confirmation Signals

Marcos sabe que a troca funcionou por 3 sinais visuais (todos em componentes existentes):

1. **Nome da igreja no header** — TenantSwitcherTrigger (08.3-T1) mostra o nome da igreja atual
2. **Dados do radar** — participantes, sinais, grupos são exclusivos deste tenant (RLS)
3. **Role na experiência** — layout muda conforme role (sidebar admin vs bottom tabs líder/participante)

**Nenhum toast, banner, ou mensagem explícita de "Você entrou na Igreja X".** O contexto visual é a confirmação. Consistente com 07.5 (silêncio como confirmação).

## Edge Cases

| Case | Behavior |
|------|----------|
| **Role diferente por tenant** | ExperienceResolver redireciona para experiência correspondente (ex: gestao → consumo). Transição de layout é perceptível mas intencional — o role label no cartão (08.2/08.3) já avisou. |
| **Tenant sem dados (novo)** | Experiência carrega com empty states nativos de cada tela (01.2 inbox zero, 06.4 welcome message, etc.) |
| **Cookie não setado** | Redirect para `/selecionar-igreja` (08.2) |
| **Tenant dissociado (race condition)** | 403 → redirect para `/selecionar-igreja` com toast: "Essa comunidade não está mais disponível." |

| Translation Key | PT-BR |
|-----------------|-------|
| `context.error.dissociated` | "Essa comunidade não está mais disponível." |

## Technical Notes

- **RLS isolation:** Após set do `tenant_id` no cookie, TODA query via Prisma extension filtra por esse tenant. Zero dado cross-tenant possível. Story 2.6 garante isolamento absoluto.
- **AsyncLocalStorage:** Middleware Next.js lê `tenant_id` do cookie e injeta no `RequestContext`. Todas as camadas downstream (API routes, server components) herdam automaticamente.
- **ExperienceResolver:** Mesmo middleware de 01.1, 03.1, 06.3, 07.5. Branch adicional: ler role do `user_tenants` filtrado por `tenant_id` ativo.
- **Veto permanente:** Zero dado de um tenant visível no contexto de outro. Admin da Igreja A nunca vê que Marcos também pertence à Igreja B.
