## Overview

**Page Purpose:** Componente de troca de igreja mid-session. Acessível em 1 tap no header da navegação. Mostra lista de igrejas associadas com indicação de qual está ativa. Marcos toca na igreja desejada → contexto troca imediatamente, sem logout, sem re-auth.

**User Situation:** Quarta à noite, 19h45. Marcos está no radar da Igreja Vida Nova. Lembra que precisa ver o radar da Igreja Graça Plena antes da reunião das 20h. Precisa trocar em ≤2 segundos.

**Success Criteria:** Em ≤2 segundos, Marcos troca de igreja e vê os dados corretos da nova comunidade. Zero logout. Zero re-auth.

**Entry Points:**
- (1) Toque no nome da igreja no header (mobile: bottom tabs area / desktop: sidebar header)

**Exit Points:**
- (1) Toque em outra igreja → context switch → 08.4
- (2) Dismiss (swipe down mobile / click outside desktop) → volta ao contexto atual

**DDR resolved:** Tenant switcher posicionado como elemento tappable no header da navegação. Nome da igreja visível, 1 tap para abrir. Padrão visual: workspace selector (Slack/Notion).

---

## Reference Materials

**Strategic Foundation:**
- FR10 / Story 2.5 AC #4 — "Tenant switcher allows selection; context switches immediately"
- Story 2.6 — RLS isolation
- DDR 2 do outline 08

**Design Constraints:**
- **1 tap** para abrir o switcher (veto permanente: ≤1 tap do header)
- **≤2s** para completar a troca
- **Zero logout/re-auth** (veto permanente)
- **Zero mensagem de "saída"** — troca é natural, não é abandono
- **Cache invalidation** transparente (DDR 3)
- **Só aparece se `user_tenants.count > 1`** — escondido para single-tenant
- NFRs: WCAG AA

## Cache Invalidation Strategy (DDR 3 Resolved)

```
[Toque em "Igreja Graça Plena"]
    │
    ├── POST /api/v1/auth/select-tenant → set cookie tenant_id
    │
    ├── TanStack Query: queryClient.removeQueries()
    │   (remove ALL cached data — fresh start for new tenant)
    │
    ├── Zustand: reset stores que dependem de tenant
    │   (useMeetingStore, usePastoralStore, etc.)
    │
    └── Router: redirect → ExperienceResolver → experiência por role
```

**Design decision:** `removeQueries()` em vez de `invalidateQueries()` — dados do tenant anterior devem ser completamente limpos, não refetched. Se Marcos voltar para o tenant anterior, TanStack Query faz fetch fresco (cache miss aceitável para segurança).

**Alternativa considerada e rejeitada:** `tenant_id` como prefixo de query key (`['groups', tenantId]`). Seria mais eficiente (cache preservado por tenant), mas risco de dados stale do tenant anterior persistindo em memória. Para MVP, cleanup total é mais seguro.

## Technical Notes

- **Trigger visibility:** Componente `TenantSwitcherTrigger` verifica `user_tenants.count > 1` client-side (dados cacheados do login). Se 1, não renderiza.
- **Bottom sheet:** Radix `Sheet` (mobile) / Radix `DropdownMenu` (desktop). shadcn/ui primitives.
- **Cache:** `queryClient.removeQueries()` global on switch. Zustand stores com `reset()` method.
- **Cookie:** `tenant_id` em cookie HttpOnly, SameSite=Strict. Middleware Next.js lê e injeta no RequestContext via AsyncLocalStorage.
- **Role mapping:** Backend retorna role enum (`LEADER`, `ADMIN_TENANT`, `PARTICIPANT`). Frontend mapeia para translation keys pastorais.
- **Accessibility:** WCAG AA. Bottom sheet com `role="dialog"`, `aria-label`. Cards com `role="option"`. Active card com `aria-selected`.
- **Domain event:** `tenant.switch.completed` com `{ fromTenantId, toTenantId, switchDurationMs, source: "switcher" }`.
