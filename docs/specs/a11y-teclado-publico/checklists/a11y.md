# A11y Checklist: Keyboard Navigation — Public Flows & Infrastructure

**Purpose**: Validar QUALIDADE DOS REQUISITOS (clareza, completude, mensurabilidade, consistência,
cobertura de edge cases) para a feature `a11y-teclado-publico` conforme WCAG 2.1 AA.
Este checklist NÃO testa implementação — testa se os requisitos escritos estão aptos
para guiar implementação e revisão sem ambiguidade.

**Created**: 2026-06-16
**Feature**: [docs/specs/a11y-teclado-publico/spec.md](../spec.md)
**Plan**: [docs/specs/a11y-teclado-publico/plan.md](../plan.md)
**Domain**: a11y (+ UX onde aplicável)

- [ ] CHK005 - Existe requisito cobrindo o comportamento de Shift+Tab (tabulação reversa) nos
  formulários de login e registro?
  [Completude, Gap, Spec §Edge Cases] {auto}

- [x] CHK007 - Existe requisito ou decisão documentada cobrindo o caso de múltiplos menus

  > não é um requisito verificável. [Gap] — mesmo patamar do CHK005/CHK006: narrativa sem FR.

## 2. Clareza e Especificidade dos Requisitos

- [x] CHK008 - "Visually hidden at rest and visible on focus" em FR-001 está quantificado com
  critérios mensuráveis de visibilidade (contraste, z-index, cobertura de conteúdo)?
  [Clareza, Spec §FR-001 + US1 AC1] {auto}
  > Evidência: US1/AC1 especifica: "fundo sólido opaco sobre qualquer conteúdo, z-index
  > superior a todos os elementos, contraste de texto >= 4.5:1 WCAG AA". Plan §Task1 CSS:
  > `z-index: 9999`, `background: white (solid opaque — WCAG contrast >= 4.5:1)`. Suficiente.

- [x] CHK009 - "Visible focus indicator" / ":focus-visible compliant" em FR-004 está quantificado
  (ex: cor de contorno, largura mínima) ou está delegado com justificativa explícita?
  [Clareza, Spec §FR-004] {auto}
  > Evidência: FR-004 diz ":focus-visible compliant with WCAG 2.1 AA - not suppressed for
  > keyboard users". US2/AC2 e US3/AC3 falam em "anel de foco visível com contraste suficiente
  > para distinguir do fundo". Plan §Task2: "Only ensure no `outline: none` suppression exists".
  > Quantificação mínima presente (WCAG AA contraste, não supressão). Global standardization
  > → Story 12.3 (explicitamente delegado). Aceitável dado escopo limitado.

- [x] CHK010 - "Confine keyboard focus within the dialog" em FR-006 especifica quais elementos
  fazem parte do ciclo de foco (todos os interativos do modal, incluindo o botão de fechar)?
  [Clareza, Spec §FR-006 + US4/AC1] {auto}
  > Evidência: US4/AC1: "foco cicla exclusivamente entre os elementos interativos do modal
  > (não alcança elementos externos enquanto o modal está visível)". Spec §Edge Cases menciona
  > "dropdown dentro de modal" como edge case. Plan §Task4: "Tab cycles only within modal
  > (focus does not escape)". A definição "elementos interativos do modal" é suficientemente
  > clara para Radix Dialog nativo. Aceitável.

- [ ] CHK011 - FR-009 especifica o comportamento de Arrow Home/End (início/fim da lista) e
  Arrow Left/Right para dropdowns com submenus ou itens agrupados?
  [Clareza, Spec §FR-009] {auto}
  > [Gap] parcial: FR-009 cobre Arrow Down/Up, Enter e Escape — conjunto mínimo do ARIA
  > Authoring Practices para DropdownMenu. Arrow Home/End não são citados. Para Radix
  > DropdownMenu o suporte é nativo (implementado), mas o requisito não especifica se é
  > esperado ou explicitamente excluído. Para a fase de validação (US5), o implementador
  > pode não testar Home/End sem referência no requisito.

- [x] CHK012 - "Stable during SSR hydration" em FR-011 tem critério operacional definindo
  o que conta como "instabilidade" (foco muda de elemento) vs. comportamento aceitável?
  [Clareza, Spec §FR-011 + US6/AC2] {auto}
  > Evidência: US6/AC2: "o foco permanece no elemento esperado, sem saltos para outras
  > partes da página". Plan §Task6: "Avoid `autoFocus` on elements that change during
  > hydration". Definição operacional: foco não muda de elemento = estável. Suficiente
  > para implementação e teste E2E.

- [ ] CHK013 - FR-001 especifica o texto exato do link skip-nav ou delega ao i18n com referência
  ao arquivo de mensagens PT-BR?
  [Clareza, Spec §FR-001] {auto}
  > [Gap] menor: FR-001 não menciona o texto. Plan §Task1 hardcoda "Ir para o conteúdo"
  > no snippet de código. A constraint do projeto (CLAUDE.md) exige textos ao usuário em
  > `apps/web/messages/pt-BR.json`. O plan não referencia o arquivo i18n — o implementador
  > pode hardcodar a string em vez de usar o sistema de internacionalização. Recomendação:
  > adicionar à spec que o texto deve vir de `messages/pt-BR.json` (chave sugerida:
  > `a11y.skipNav.label`).

- [x] CHK014 - "At most 2 Tab presses from page load" em SC-001 é uma definição mensurável
  e verificável no contexto do layout real (SkipNav como 1º elemento focável)?
  [Clareza, Spec §SC-001] {auto}
  > Evidência: SC-001: "at most 2 Tab presses from page load (via skip navigation)".
  > Interpretação: Tab1 = foca skip-nav link; Tab2 = próximo elemento (se não ativar).
  > Mas via Enter após Tab1 → foco vai para #conteudo = 1 Tab + 1 Enter. O critério é
  > verificável via test E2E (plan: `await page.keyboard.press('Tab')` → skip-nav focado
  > → `Enter` → `#conteudo` focado). Mensurável.

  (role="dialog" + aria-modal="true") sem sobreposição ou conflito?

- [x] CHK016 - A decisão Q1 (dec-012: cross-browser apenas manual via SC-008, CI apenas

  > Plan §Task9: checklist manual Chrome/Firefox/Safari. SC-007: "Chromium only —

- [x] CHK017 - FR-010 (skeletons não focáveis) e FR-011 (estabilidade durante hidratação) são

  > "Radix Dialog provides native focus trap — validate, do NOT reimplement". Plan §Task5:
  > "Radix UI via shadcn... Validate existing Radix components, fix gaps only." Consistente.

- [x] CHK019 - FR-013 (mínimo 3 modais) e US4/AC4 (3 modais listados: confirmação, criar grupo,
  configurações) são consistentes com a disponibilidade real desses modais na aplicação?

  > com "Settings modal (or any third distinct modal)". Consistente com a realidade de um
  > projeto em pré-implementação. [Assumption] registrada no plan.

## 4. Mensurabilidade dos Critérios de Aceitação

- [x] CHK020 - SC-002 ("login completable end-to-end using only keyboard") tem critério de
  término definido (o que conta como "completado")?
  [Mensurabilidade, Spec §SC-002] {auto}
  > Evidência: SC-002: "field-fill → submit → result". US2/AC3: "Enter submete o formulário —
  > o mesmo comportamento de um clique com mouse". Test independente de US2: "Verificar que
  > Enter submete o formulário". "Result" = formulário enviado (implícito: resposta da API ou
  > redirecionamento). Mensurável via E2E: `await page.keyboard.press('Enter')` → verificar
  > navegação ou resposta de sucesso.

- [x] CHK021 - SC-004 ("100% of tested modal dialogs — minimum 3") tem critério claro de
  cobertura mínima e o que constitui "trap focus correctly"?
  [Mensurabilidade, Spec §SC-004 + FR-013] {auto}
  > Evidência: SC-004: "100% of tested modal dialogs (minimum 3) trap focus correctly and
  > return focus to trigger on close". FR-013 define "minimum 3". US4/AC1/AC2 definem o que
  > é "correctly": Tab cicla apenas dentro do modal; Escape retorna foco ao trigger.
  > E2E test `modal-focus-trap.spec.ts` cobre os 3. Mensurável.

- [x] CHK022 - SC-006 ("zero new violations introduced") define explicitamente o escopo de
  comparação (apenas fluxos públicos ou toda a aplicação)?
  [Mensurabilidade, Spec §SC-006 + FR-012] {auto}
  > Evidência: FR-012: "automated accessibility scan baseline report of all public flows".
  > Plan §Task0: "Flows audited: /, /login, /register (all public routes under
  > (public)/(marketing))". Plan §Task7: delta-report compara com baseline do Task0.
  > Escopo de comparação = fluxos públicos. Mensurável e delimitado.

- [x] CHK023 - SC-007 ("all 6 functional areas have corresponding E2E tests that pass in CI")
  lista explicitamente os 6 arquivos de teste correspondentes?
  [Mensurabilidade, Spec §SC-007 + Plan §Task8] {auto}
  > Evidência: Plan §Task8 lista 6 arquivos exatos: skip-nav.spec.ts, login-keyboard.spec.ts,
  > register-keyboard.spec.ts, modal-focus-trap.spec.ts, dropdown-keyboard.spec.ts,
  > skeleton-focus.spec.ts. 1:1 com as 6 áreas funcionais. Rastreabilidade completa.

- [ ] CHK024 - SC-008 (manual checklist cross-browser) define critério objetivo de aprovação
  (ex: zero blockers, máximo de N majors aceitos)?
  [Mensurabilidade, Spec §SC-008] {auto}
  > [Gap]: SC-008 define severidades (blocker/major/minor) mas não define o critério de
  > aprovação. "All keyboard navigation scenarios must pass the manual checklist" com
  > "severity classification" não especifica: zero blockers = aprovado? 1 minor aceitável?
  > Um implementador não sabe quando o checklist manual "passou". Recomendação: adicionar
  > critério de gate explícito, ex: "zero blockers; majors documentados como tech debt
  > com ticket aberto; minors aceitáveis com justificativa".

## 5. Cobertura de Edge Cases

- [x] CHK025 - O edge case de Shift+Tab (ordem reversa) está pelo menos registrado na spec,
  mesmo que sem FR formal?
  [Cobertura, Spec §Edge Cases] {auto}
  > Evidência: Spec §Edge Cases: "O que acontece se o usuário pressionar Shift+Tab? A ordem
  > de foco deve ser o inverso da ordem de tabulação para frente (WCAG 2.1 AA 2.4.3)".
  > Registrado como edge case com critério esperado e referência WCAG. Não tem FR/AC —
  > ver CHK005 para gap. Como registro de edge case: presente.

- [x] CHK026 - O edge case de trigger removido do DOM após fechar modal está registrado?
  [Cobertura, Spec §Edge Cases] {auto}
  > Evidência: Spec §Edge Cases descreve o cenário e a resposta esperada ("foco deve mover
  > para o elemento mais próximo significativo"). Não há FR correspondente — ver CHK006.

- [x] CHK027 - O edge case de skeletons parcialmente hidratados (mix de reais e placeholders)
  está registrado nos requisitos?
  [Cobertura, Spec §Edge Cases] {auto}
  > Evidência: Spec §Edge Cases: "Skeletons parciais: alguns itens já hidrataram, outros
  > ainda são skeletons — o Tab não deve misturar focáveis reais com placeholders."
  > Plan §Task6 não menciona explicitamente este sub-caso, mas a solução (aria-hidden ou
  > tabindex=-1 em todos os skeletons) cobre o caso parcial também.

- [ ] CHK028 - Os 3 edge cases listados em §Edge Cases que não têm FR correspondente (Shift+Tab,
  trigger removido, múltiplos menus) estão explicitamente marcados como "aceitos sem FR" ou
  "a cobrir via teste manual" para evitar ambiguidade no backlog?
  [Cobertura, Ambiguity, Spec §Edge Cases] {auto}
  > [Ambiguity]: A seção §Edge Cases da spec lista 5 cenários, mas nenhum tem FR ou AC
  > explícito. Os implementadores podem interpretar como "requisitos implícitos" ou como
  > "informação de contexto não vinculante". Recomendação: adicionar uma nota na spec:
  > "Edge cases sem FR correspondente são documentados como contexto; comportamento esperado
  > é descritivo, não normativo. Tratamento formal via Story 12.2 (autenticados) ou
  > próxima iteração."

## 6. Requisitos Não-Funcionais e Conformidade WCAG

- [x] CHK029 - A versão alvo de WCAG está especificada (2.1 AA vs. 2.2 vs. 3.0)?
  [Completude, Spec §Status/FR-004] {auto}
  > Evidência: Spec header: "NFR-A1 (WCAG 2.1 AA - Keyboard Navigation)". FR-004:
  > ":focus-visible compliant with WCAG 2.1 AA". SC-001 referencia critério WCAG 2.4.1
  > implicitamente (2 Tab presses). WCAG 2.1 AA é o alvo declarado em toda a spec.

- [x] CHK030 - Os critérios WCAG 2.1 AA relevantes para cada FR estão explicitamente citados
  ou deriváveis sem ambiguidade?
  [Completude, Spec §FR-001..FR-013] {auto}
  > Evidência: US1 §Why: "WCAG 2.1 AA (critério 2.4.1 - Bypass Blocks)". US4 §Why:
  > "WCAG 2.1 AA (2.1.2 - No Keyboard Trap)". SC-001: "via skip navigation" (2.4.1).
  > Spec §Edge Cases: "WCAG 2.1 AA 2.4.3" (Shift+Tab). FR-004: "WCAG 2.1 AA". Cobertura
  > satisfatória — principais critérios mapeados. FR-008 (role=dialog) deriva de ARIA
  > Authoring Practices (implícito, aceitável).

- [x] CHK031 - A ferramenta de scan axe-core (e não outra) está especificada como o mecanismo
  de validação automatizada, com referência ao pacote exato?
  [Clareza, Spec §FR-012 + Plan §Task0] {auto}
  > Evidência: Plan §Task0: "Package: @axe-core/playwright (already installed per
  > RECONCILIACAO-EPIC12.md)". Ferramenta e versão do pacote especificadas. A spec não
  > menciona o pacote diretamente (menciona apenas "automated accessibility scan" em FR-012),
  > mas o plan resolve a especificidade. Aceitável.

- [ ] CHK032 - Existe requisito especificando o threshold de violações axe-core no relatório
  baseline (ex: nenhuma violação de impacto "critical" pré-existente deve ser introduzida
  pelas mudanças desta story)?
  [Completude, Gap, Spec §SC-006] {auto}
  > [Gap]: SC-006 define "zero new violations introduced by this story's changes", mas não
  > especifica como distinguir violações pré-existentes das novas. O mecanismo de distinção
  > é o delta (baseline vs. final), mas o requisito não menciona como classificar violações
  > presentes no baseline (ignorar? documentar? escalar se critical?). Plan §Task7 menciona
  > `axe-delta-report.md` com "violations resolved, violations new (must = 0), tech debt
  > accepted", o que mitiga parcialmente. Recomendação: adicionar à spec que violações
  > pré-existentes no baseline são aceitas como tech debt e documentadas no delta-report,
  > sem bloquear a story.
