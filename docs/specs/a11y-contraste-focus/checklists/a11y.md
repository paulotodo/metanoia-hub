## Categoria 2 — Clareza e Ausencia de Ambiguidade

- [ ] CHK006 - O termo "texto de leitura" (vs. decorativo/nao-textual) tem criterio verificavel que distingue os dois para aplicacao da troca text-muted para text-secondary? [Ambiguity, Plan §Eixo B, §B1] {auto}
  > [Ambiguity] — Plan §B1 menciona "manter muted apenas em conteudo decorativo/nao-textual (ex: icone + do FAQ:29)" como unico exemplo, sem regra geral. Implementadores podem divergir ao julgar outros elementos de marketing/. Sugestao: adicionar heuristica "se o elemento comunica informacao textual ao leitor, usar text-secondary; se e puramente ornamental/iconografico, text-muted e permitido".

- [x] CHK007 - O utilitario canonico de focus-ring (SC-3.2) e declarado como string literal unica sem variantes permitidas? [Clareza, Spec §SC-3.2; Plan §C1] {auto}
  > Spec SC-3.2 declara o utilitario exato: focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-brand-teal/30 focus-visible:ring-offset-2. "Nenhum outro padrao de ring e aceito em novos componentes." Sem ambiguidade.

- [ ] CHK008 - Os casos manuais do codemod focus-ring sao enumerados exaustivamente ou apenas exemplificados? [Ambiguity, Plan §C3] {auto}
  > [Ambiguity] — Plan §C3 lista 4 casos explicitos (ring-red-500 em delete-group-dialog.tsx:106, ring-brand-primary/30 em OnboardingWizard.tsx:181, focus-within:ring-primary em trail-card.tsx:56, ring-blue-500 1x). A declaracao "~5-10 casos manuais" implica que pode haver mais nao mapeados. O dry-run do script devera produzir a lista definitiva antes da execucao do codemod.

- [ ] CHK009 - O gate CI "hard fail vs warn" (R7) tem a lista de pares hard-gated enumerada explicitamente na spec/plan? [Clareza, Plan §D1, §R7] {auto}
  > [Gap] — Plan §D1 declara "fail nos pares corrigidos por esta feature; warn no restante" mas a lista exata de pares hard-gated nao esta enumerada. Implementador precisara derivar dos FRs: {text-secondary x surface-base >=4.5, text-primary x care-attention >=4.5, text-primary x care-ok >=4.5, brand-teal x surface-elevated >=3}. Recomenda-se declarar a matriz explicitamente em check-contrast-tokens.mjs e referencia-la na spec/plan.

- [x] CHK010 - "Texto grande" (SC-2.4) esta quantificado conforme WCAG 2.1 (>=24px regular OU >=18px bold)? [Clareza, Spec §SC-2.4] {auto}
  > SC-2.4 declara explicitamente "tamanho grande (>=24px regular ou >=18px bold)". Alinhado com WCAG 1.4.3 definicao de large text.

- [ ] CHK011 - O criterio "nenhum outro padrao de ring e aceito em novos componentes" (SC-3.2) tem mecanismo de enforcement definido alem do grep de variantes antigas? [Clareza, Spec §SC-3.2; Plan §T6, §NFR-MANUT] {auto}
  > [Gap] — NFR-MANUT cita grep de variantes legadas. Porem, nenhum item previne a introducao de novas variantes ad-hoc (ring-teal-600, ring-custom-*) em PRs futuros. Seria necessario lint-rule que proiba qualquer focus-visible:ring-* fora do canonico, nao apenas variantes conhecidas.

- [ ] CHK014 - A estrategia de remediacao do text-muted e consistente entre spec (FR-03 "ajustar token") e plan (trocar classes nos componentes)? [Conflict, Spec §FR-03; Plan §R5, §Eixo B, §B1] {auto}

Acao recomendada: corrigir FR-03 na spec para "Substituir uso de text-muted por text-secondary em texto de leitura em components/marketing/".

## Categoria 5 — Cobertura de Cenarios e Edge Cases

- [ ] CHK020 - O codemod (Eixo C) define comportamento para arquivos com multiplas variantes de ring diferentes na mesma linha/className? [Cobertura, Plan §C2] {auto}
  > [Gap] — Plan §C2 define o script codemod-focus-ring.mjs com dry-run + apply, mas nao especifica comportamento quando uma mesma string className contem mais de uma variante distinta (ex: ring-ring ring-red-500 — uma para substituir, outra para preservar). O dry-run devera mapear esses casos antes da execucao.

- [x] CHK021 - O cenario de rota autenticada (/dashboard, grupos) no E2E esta coberto ou explicitamente excluido com justificativa tecnica? [Cobertura, Spec §SC-5.1; Plan §D2] {auto}
  > Plan §D2 declara padrao ISOLADO/route-interception para rotas autenticadas. SC-5.1 lista /dashboard e grupos como "se possivel". Plano justifica: "specs autenticados com goto sem login falham" — padrao estabelecido por a11y-teclado-autenticado (Story 12.1).

- [x] CHK022 - O cenario brand-teal-light (#3aafa9, 2.55:1) como fundo decorativo (nao-texto) esta coberto nos requisitos de uso permitido? [Cobertura, Spec §SC-2.5; Plan §Eixo A] {auto}
  > FR-06 e SC-2.5 restringem uso como texto. Plan §Eixo A: "so fundo/decorativo". Uso decorativo e permitido por escopo — WCAG 1.4.3 aplica-se a texto, nao a decoracao.

- [x] CHK023 - care-urgent (#c1666b, 3.73:1) como texto tem requisito de tamanho minimo documentado conforme WCAG? [Cobertura, Spec §SC-2.4] {auto}
  > SC-2.4 define: "para uso como texto, documentar restricao a tamanho grande (>=24px regular ou >=18px bold)". Alinhado com WCAG 1.4.3 large text threshold (3:1).

- [x] CHK024 - O link "Esqueceu a senha?" em /login — o requisito especifica underline permanente (nao apenas hover/focus)? [Cobertura, Spec §SC-1.2; Plan §B2] {auto}
  > SC-1.2: "possui underline permanente ou indicador visual nao-cromatico". Plan §B2: "Adicionar underline underline-offset-2 permanente (nao depender de cor)". Permanente = sempre visivel, independente de estado de interacao.

- [ ] CHK025 - ring-primary (14x no grep, Plan §R4) tem estrategia de tratamento explicita na spec/plan (substituir ou preservar como caso manual)? [Cobertura, Plan §R4, §C2, §C3] {auto}
  > [Gap] — Plan §R4 lista ring-primary com 14 ocorrencias, mas §C2 (codemod global) e §C3 (casos manuais a preservar) nao mencionam ring-primary explicitamente. Nao esta claro se e alias de brand-teal (substituir) ou variante semantica (preservar). O dry-run do codemod devera classificar cada ocorrencia.
