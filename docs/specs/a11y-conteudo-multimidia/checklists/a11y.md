# A11Y Checklist: a11y-conteudo-multimidia (Story 15.5)

**Purpose**: Valida a qualidade dos requisitos de acessibilidade — hierarquia semântica, contraste, foco, ícones, animações, ARIA e experiência de teclado para as 3 frentes (Lesson Viewer, Plyr, Governança alt-text).
**Created**: 2026-06-25
**Feature**: [spec.md](../spec.md)

---

## Hierarquia Semântica e Estrutura de Página

- [x] CHK001 - O requisito de `<h1>` único por página está definido com valor concreto (nome da aula)? [Completude, Spec §FR-003, CA-001.2] {auto}
  > Evidência: FR-003 "``<h1>`` = nome da aula; único por página"; CA-001.2 "`<h1>` contém o nome da aula (único por página)".

- [x] CHK002 - Está especificado o nível de heading (`<h2>`) para seções de rich_text, impedindo salto de nível? [Completude, Spec §CA-003.1, NFR-A4] {auto}
  > Evidência: CA-003.1 "contentType = rich_text — conteúdo renderizado com `<h2>` para seções, sem saltar níveis"; NFR-A4 "Hierarquia de headings sem saltar nível (WCAG 1.3.1)".

- [ ] CHK003 - Estão definidos os requisitos de heading para o painel de atalhos do Plyr (tecla "?") — qual é o nível semântico do título do `<dialog>`? [Completude, Spec §FR-006, Gap] {auto}
  > [Gap]: FR-006 menciona "tabela acessível" mas não especifica se há `<h2>` ou `<dialog>` com título via `aria-labelledby`. Plan §3.3 cita `<dialog>` com `<table>`, mas omite o título semântico do diálogo.

- [x] CHK004 - Estão definidos requisitos de hierarquia para o `<h1>` da página admin `/admin/accessibility-gaps` em coexistência com os headings da tabela de resultados? [Completude, Spec §FR-016, Plan §3.1.4] {auto}
  > Evidência: FR-016 define a página; Plan §3.1.4 lista textos PT-BR com `title` ("Conteúdo com Acessibilidade Incompleta") e `columns`. Estrutura implica `<h1>` + `<table>` com `<th>` — estrutura semântica adequada.

## Contraste e Visibilidade

- [x] CHK005 - O requisito de contraste mínimo 4.5:1 (texto normal) e 3:1 (UI) está documentado como NFR? [Completude, Spec §NFR-A5] {auto}
  > Evidência: NFR-A5 "Contraste mínimo 4.5:1 (texto normal), 3:1 (UI) — WCAG 1.4.3".

- [ ] CHK006 - Está especificado se o estado de "aula com problemas de acessibilidade" na tabela admin usa cor como único indicador visual (violaria WCAG 1.4.1 — Use of Color)? [Clareza, Spec §FR-016, Ambiguity] {auto}
  > [Ambiguity]: Spec/Plan descrevem apenas "tabela de aulas com alt-text ausente", sem especificar se linhas com `has_missing_alt_text=true` são sinalizadas visualmente por cor ou ícone + texto. WCAG 1.4.1 exige que cor não seja o único diferenciador.

- [x] CHK007 - O requisito de contraste se aplica explicitamente a todos os novos componentes (LessonViewer, PlyrVideoPlayer, AccessibilityGapsList, LessonNavigationButton)? [Completude, Spec §NFR-A5] {auto}
  > Evidência: NFR-A5 é global — "Contraste mínimo 4.5:1"; Frente A menciona "contraste ≥ 4.5:1" explicitamente na checklist de gates da frente A (Spec §2, Frente A, "Gate a11y").

## Focus Management

- [x] CHK008 - Está definido o comportamento de foco ao fim do vídeo (mover para nextModuleButtonRef se existir)? [Completude, Spec §FR-004, CA-001.4] {auto}
  > Evidência: CA-001.4 "Ao fim do vídeo, foco move para o botão 'Próxima aula' se existente"; FR-004 "Botão 'Próxima aula'/'Próximo módulo' com `nextModuleButtonRef` e foco pós-vídeo".

- [ ] CHK009 - Está definido o comportamento de foco quando o painel de atalhos (tecla "?") é FECHADO — para onde retorna o foco? [Completude, Spec §FR-006, Gap] {auto}
  > [Gap]: FR-006 define abertura do painel com "?", e Plan §3.3 cita `<dialog>` controlado por estado. Mas não está especificado que o foco retorna ao botão "?" ou ao último elemento ativo ao fechar o diálogo. Sem isso, usuários de teclado perdem a posição.

- [x] CHK010 - O requisito de focus-ring visível em todos os interativos está documentado como NFR? [Completude, Spec §NFR-A7] {auto}
  > Evidência: NFR-A7 "Focus-ring visível em todos os interativos — WCAG 2.4.7"; Frente A menciona gate a11y "focus-ring" explicitamente.

- [ ] CHK011 - Está definido o comportamento de foco ao navegar entre os 4 contentTypes no lesson-viewer (ex: mudar de vídeo para rich_text — o foco deve ir para o `<h1>` ou para o início do conteúdo)? [Completude, Spec §FR-002, Gap] {auto}
  > [Gap]: FR-002 define switch por contentType, mas não especifica onde o foco deve estar após a mudança de conteúdo (se ocorrer navegação intra-página). Para navegações SPA onde o conteúdo muda sem reload, WCAG 2.4.3 (Focus Order) exige que o foco seja gerenciado explicitamente.

## Ícones e Elementos Decorativos

- [x] CHK012 - O requisito de `aria-hidden="true"` e `focusable="false"` para ícones decorativos está documentado como NFR? [Completude, Spec §NFR-A8] {auto}
  > Evidência: NFR-A8 "Ícones decorativos com `aria-hidden='true'` e `focusable='false'` — WCAG 1.1.1".

- [x] CHK013 - O ícone de link externo no `ExternalLinkView` tem requisito explícito de `aria-hidden`? [Completude, Spec §CA-003.3] {auto}
  > Evidência: CA-003.3 "contentType = external_link — link descritivo `aria-label='Acessar recurso externo: {nome}'`, ícone `aria-hidden='true'`".

- [ ] CHK014 - Estão definidos requisitos para o ícone/indicador visual do botão de atalhos ("?") do Plyr — `aria-label` no botão que abre o painel? [Completude, Spec §FR-006, Gap] {auto}
  > [Gap]: FR-006 define que "tecla '?' abre painel de atalhos" mas não especifica o `aria-label` do botão UI que representa essa ação (ex: "Atalhos de teclado" ou "Ver atalhos"). Usuários de leitor de tela que não sabem do atalho "?" precisam descobrir o botão por seu rótulo.

## ARIA e Semântica

- [x] CHK015 - O requisito de `role="slider"` e `aria-valuenow` no scrubber do Plyr está especificado como nativo da biblioteca (sem markup manual)? [Completude, Spec §CA-002.2, FR-005] {auto}
  > Evidência: CA-002.2 "Scrubber de progresso tem `role='slider'` e `aria-valuenow` (fornecido pelo Plyr nativamente)"; Spec §2 Frente B "role=slider+aria-valuenow (Plyr nativo)".

- [x] CHK016 - O requisito de `aria-label` nos botões i18n PT-BR do Plyr está especificado com valores concretos? [Clareza, Spec §CA-002.1, Plan §3.3] {auto}
  > Evidência: CA-002.1 lista todos os labels: "Reproduzir, Pausar, Volume, Mudo, Tela cheia, Avançar 10s, Retroceder 10s"; Plan §3.3 detalha o objeto `i18n` com valores literais PT-BR.

- [x] CHK017 - O requisito de `aria-label` em elemento interativo (nunca em `<div>`/`<span>` genérico) está documentado como convenção inegociável? [Completude, Spec §6] {auto}
  > Evidência: Spec §6 Convenções "aria-label em elemento **interativo** (nunca em `<div>`/`<span>` genérico)".

- [ ] CHK018 - Está definido se a região `aria-live` para anúncio de conclusão de vídeo (já existente em `video-player.tsx`) deve ser reutilizada ou recriada no `plyr-video-player.tsx`? [Completude, Spec §FR-005, Gap] {auto}
  > [Gap]: O `video-player.tsx` órfão já tem `aria-live` estático para anunciar "Vídeo concluído." O `plyr-video-player.tsx` substitui esse componente mas a spec/plan não especifica explicitamente que a região `aria-live` deve ser preservada. Sem ela, o anúncio polite ao fim do vídeo é perdido.

- [x] CHK019 - O requisito de fallback alt="Imagem sem descrição" para imagens sem alt em rich_text está especificado? [Completude, Spec §FR-009, CA-003.4] {auto}
  > Evidência: FR-009 "Imagens em rich_text: fallback `alt='Imagem sem descrição'`"; CA-003.4 "Imagens em `rich_text` com fallback `alt='Imagem sem descrição'` quando `alt` vazio/ausente".

## Animações e Movimento

- [x] CHK020 - O requisito de `motion-safe:` antes de toda animação/transição está documentado como convenção obrigatória e como lição de Epics anteriores? [Completude, Spec §6, NFR-A6] {auto}
  > Evidência: NFR-A6 "`motion-safe:` em toda animação/transição — WCAG 2.3.3"; Spec §6 Convenções "Animações: **sempre** `motion-safe:` antes de `transition-*`/`animate-*`"; Spec §6 Lições 15.1-15.4 citadas no escopo original.

- [x] CHK021 - O botão `LessonNavigationButton` tem requisito explícito de `motion-safe:` nas suas transições? [Completude, Spec §2 Frente A, Plan §3.2] {auto}
  > Evidência: Spec §2 Frente A lista "Gate a11y: focus-ring, contraste ≥ 4.5:1, `motion-safe:` em toda animação" como requisito explícito da frente A; Plan §3.2 menciona "motion-safe em transições" no botão de navegação.

## Navegação por Teclado

- [x] CHK022 - O requisito de navegação Tab para o botão "Próxima aula" está especificado com critério de aceite mensurável? [Clareza, Spec §CA-001.3] {auto}
  > Evidência: CA-001.3 "Botão 'Próxima aula' / 'Próximo módulo' está visível e navegável via Tab".

- [x] CHK023 - O painel de atalhos do Plyr está especificado como `<dialog>` com `<table>` acessível — estrutura semântica que garante navegação por teclado sem aprisionamento de foco? [Completude, Spec §FR-006, Plan §3.3] {auto}
  > Evidência: Plan §3.3 "Painel de atalhos (tecla '?'): `<dialog>` com `<table>` acessível, controlado por estado". `<dialog>` nativo do HTML tem gerenciamento de foco embutido (modal focus trap) — decisão arquitetural correta.

- [ ] CHK024 - Está definido se os 4 ramos do switch de contentType (video/rich_text/pdf_doc/external_link) são todos navegáveis por teclado sem dependência de mouse? [Completude, Spec §FR-002, Gap] {auto}
  > [Gap]: A spec define a11y para cada contentType individualmente (CA-003.1/3.2/3.3), mas não há requisito explícito consolidado que garanta que TODOS os 4 ramos são completamente operáveis por teclado. `PdfViewer` usa `<iframe>` — WCAG 2.1.1 exige que iframes não aprisionem o foco (necessário `tabindex` e escape via Esc).
