# A11y Checklist: Screen Reader — Trilhas, Progresso & Conteúdo

**Purpose**: Validar a qualidade, completude e mensurabilidade dos requisitos de acessibilidade para screen readers nas telas de trilha — "unit tests for requirements".
**Created**: 2026-06-25
**Feature**: [spec.md](../spec.md) | [plan.md](../plan.md)

---

## Completude de Requisitos ARIA

- [x] CHK001 — São os requisitos de `aria-label` definidos para TODOS os componentes interativos in-scope (trail-card content, trail-card catalog, module-accordion-item, trail-progress-bar, video-player)? [Completude, Spec §FR-002, FR-003, FR-005, FR-009] {auto}
  > Evidência: FR-002 cobre trail-card content; FR-003 cobre module-accordion-item; FR-005 cobre TrailProgressBar; FR-009 cobre video-player; plan §2 cobre catalog variant. Todos os 5 componentes interativos têm requisito de label explícito.

- [x] CHK002 — São os requisitos de `aria-hidden` definidos para todos os ícones visuais que duplicariam significado se lidos pelo screen reader? [Completude, Spec §FR-004] {auto}
  > Evidência: FR-004 exige `aria-hidden="true"` em ícones de checkmark visuais. Plan §4 menciona ícone de chevron e checkmark no módulo concluído.

- [x] CHK003 — São os requisitos de `role="region"` com `aria-label` definidos para a view de summary de progresso? [Completude, Spec §FR-006] {auto}
  > Evidência: FR-006 especifica explicitamente `role="region"` com `aria-label` no topo do "Meu Progresso".

- [x] CHK004 — São os requisitos de `role="status"` / `aria-live="polite"` definidos para o componente de anúncio de conclusão de módulo? [Completude, Spec §FR-008] {auto}
  > Evidência: FR-008 especifica `role="status"`, `aria-live="polite"`, `aria-atomic`, comportamento de `sr-only` e ausência de layout shift.

- [x] CHK005 — São os requisitos de foco pós-vídeo (`ended` event) definidos, incluindo o fallback quando não há botão "Próximo módulo"? [Completude, Spec §FR-010] {auto}
  > Evidência: FR-010 especifica os dois cenários: (a) foco para "Próximo módulo" se presente, (b) retorno ao `<video>` se ausente. User Story 6 repete ambos.

- [x] CHK006 — São os requisitos de título de página (`<h1>` e/ou `document.title`) definidos para a tela de listagem de trilhas? [Completude, Spec §FR-001] {auto}
  > Evidência: FR-001 exige `<title>` e/ou `<h1>` visível anunciando "Trilhas disponíveis" ou "Minhas Trilhas". Plan §3 discute o desafio do `'use client'` e alternativas.

## Clareza de Requisitos

- [x] CHK007 — Os formatos de string de `aria-label` estão definidos com templates exatos (sem ambiguidade de ordem, separador ou capitalização)? [Clareza, Spec §FR-002, FR-003] {auto}
  > Evidência: FR-002 define `"Trilha: {name}, {status label}, {progress}% concluída, {n} módulos"`. FR-003 define `"Módulo {n} de {total}: {name} — {status}"`. Ambos com template literal explícito.

- [x] CHK008 — O mapeamento de valores de status de enum para labels PT-BR está definido (ex: `not_started` → "Não Iniciada")? [Clareza, Spec §US1-AC3, §FR-003] {auto}
  > Evidência: US1-AC3 define "Não Iniciada" para trail status. FR-003 lista "Concluído", "Em andamento", "Bloqueado" para módulos. Plan §4 adiciona "Não iniciado" para módulos sem progresso.

- [x] CHK009 — O requisito de `label` obrigatório no `TrailProgressBar` especifica que o default genérico atual deve ser REMOVIDO (não apenas depreciado)? [Clareza, Spec §FR-005, Plan §5] {auto}
  > Evidência: Plan §5 define "Tornar `label` **obrigatório** (remover o `?` do tipo e o default genérico)". Clareza suficiente para implementação.

- [x] CHK010 — O requisito de anúncio de conclusão de módulo (FR-008) especifica o comportamento de reset do `message` para evitar re-anúncios em re-renders? [Clareza, Spec §FR-008, Plan §8] {auto}
  > Evidência: Plan §8 define "A limpeza do `message` (reset para `""`) deve acontecer após timeout (~3s)". O `~3s` é uma aproximação; aceitável para um componente de anúncio polite.

- [ ] CHK011 — O requisito FR-007 (lesson items no "Meu Progresso") especifica se o nome da aula deve vir do campo `lessonName` do tipo ou de um fallback? [Clareza, Spec §FR-007, Plan §6] [Ambiguity] {auto}
  > Gap identificado: Plan §6 admite que `ModuleProgressDetail.lessons[].lessonName` pode não existir em `@metanoia/types` e propõe fallback `"Aula {index+1}: {statusLabel}"`. FR-007 não menciona este fallback. A spec não define o fallback explicitamente — implementador precisará decidir em runtime sem contrato claro. Ação: confirmar em código se `lessonName` existe antes de implementar; se não existir, documentar o fallback na spec antes de executar FR-007.

- [x] CHK012 — O requisito de `aria-label` contextual para módulos no `TrailProgressBar` (dentro do accordion) está diferenciado do label da barra de trilha overall? [Clareza, Spec §US2-AC3, FR-005] {auto}
  > Evidência: US2-AC3 define "Progresso no módulo: {n}%"; Plan §5 define "Progresso no módulo {module name}: {x}%". FR-005 exige label contextual por instância. Distingue claramente trail overall vs. per-module.

## Consistência de Requisitos

- [x] CHK013 — Os templates de `aria-label` para trail-card (content variant) e trail-card (catalog variant) são consistentes em estrutura — ambos começam com "Trilha:"? [Consistência, Spec §FR-002, Plan §2] {auto}
  > Evidência: FR-002 e Plan §2 definem ambos os variants com prefixo "Trilha:". O catalog variant omite `progressPercent` (N/A para trilhas não iniciadas) mas mantém a estrutura `"Trilha: {name}, {statusLabel}, {moduleCount} módulos"`.

- [x] CHK014 — Os requisitos de `aria-label` em `video-player.tsx` são consistentes com o padrão PT-BR aplicado nos demais componentes (prefixo descritivo + título)? [Consistência, Spec §FR-009, FR-003] {auto}
  > Evidência: FR-009 define `"Vídeo: {title}"` em PT-BR. Consistent com o padrão "Trilha: {name}" e "Módulo {n} de {total}: {name}". Sem conflito.

- [x] CHK015 — O requisito de `aria-atomic="true"` no `ModuleCompletionAnnounce` é consistente com a semântica de anúncio completo esperada? [Consistência, Spec §FR-008, Plan §8] {auto}
  > Evidência: Plan §8 especifica `aria-atomic="true"` e justifica que "garante que o screen reader leia o anúncio completo". Consistente com `aria-live="polite"`.

- [x] CHK016 — FR-013 (proibição de `aria-label` em `<div>`/`<span>` com `role` genérico) é consistente com a solução proposta no Plan §6 para o summary de progresso? [Consistência, Spec §FR-013, Plan §6] {auto}
  > Evidência: Plan §6 propõe `<div role="region" aria-label="...">` — `role="region"` é explícito, não genérico. Consistent com FR-013.

## Qualidade dos Critérios de Aceite

- [x] CHK017 — SC-001 é mensurável com as ferramentas disponíveis (axe-core via E2E gate `axe-quality-gate`)? [Mensurabilidade, Spec §SC-001] {auto}
  > Evidência: SC-001 referencia o gate `axe-quality-gate` existente, nas rotas `/app/consumo/trilhas` e `/app/consumo/trilhas/{trailId}`. Gate já opera em CI (Epic 12 docs confirmam).

- [x] CHK018 — SC-002 (todo `role="progressbar"` com `aria-label` não genérico) é verificável via asserção de teste automatizado, não apenas via inspeção manual? [Mensurabilidade, Spec §SC-002] {auto}
  > Evidência: SC-002 menciona "verified by a targeted axe rule check or automated test assertion". Plan §5 define a obrigatoriedade do `label` prop — TypeScript strict enforça em compile time, eliminando labels ausentes.

- [x] CHK019 — SC-003 (sign-off humano do manual-test-checklist) está claramente definido como um gate HUMANO, não automatizável? [Mensurabilidade, Spec §SC-003] {auto}
  > Evidência: SC-003 define "signed off by the operator (Paulo) as the human gate for actual screen reader behavior". Escopo explícito: VoiceOver/NVDA. Gate humano não pretende ser automatizável.

- [x] CHK020 — SC-004 especifica os três comandos exatos a serem executados (lint, test, build) para validação antes de merge? [Mensurabilidade, Spec §SC-004] {auto}
  > Evidência: SC-004 lista `pnpm turbo lint`, `pnpm --filter @metanoia/web test`, `pnpm turbo build --filter=@metanoia/web` — três comandos exatos, suficientemente específicos.

- [x] CHK021 — SC-005 (proibição de `transition-*`/`animate-*` sem `motion-safe:`) pode ser verificado por grep no código modificado? [Mensurabilidade, Spec §SC-005] {auto}
  > Evidência: SC-005 é verificável por `grep -rn "transition-\|animate-" apps/web/src/components/content/ | grep -v "motion-safe:"`. Mensurável.

## Cobertura de Cenários

- [x] CHK022 — Os três estados de loading/error/success da tela de listagem de trilhas têm requisito de `<h1>` visível em todos? [Cobertura, Spec §FR-001, Plan §3] {auto}
  > Evidência: Plan §3 identifica explicitamente: "Garantir que `<main>` sempre contenha `<h1>Minhas Trilhas</h1>` visível em todos os estados (loading, error, success)".

- [x] CHK023 — O cenário de vídeo sem título (`title` prop ausente) está coberto no requisito do video-player? [Cobertura, Spec §FR-009] {auto}
  > Evidência: FR-009 define fallback explícito: `"Vídeo da aula"` quando `title` prop não está disponível.

- [x] CHK024 — O cenário de módulo com `completionPercent === 0` (não iniciado, não bloqueado) está coberto no requisito de `aria-label` do accordion? [Cobertura, Spec §FR-003, Plan §4] {auto}
  > Evidência: Plan §4 define a lógica completa: `completionPercent === 100` → "Concluído", `> 0` → "Em andamento", bloqueado → "Bloqueado", `else` → "Não iniciado". Cobre o zero case.

- [x] CHK025 — O cenário de `useReportProgress` pendente quando vídeo termina (async gap) está coberto nos requisitos? [Cobertura, Spec §Edge Cases] {auto}
  > Evidência: Edge Case explícito: "The announcement component must handle the async gap (no announcement until the mutation resolves or the threshold is crossed server-side)". FR-008-AC3 confirma que o componente recebe `message` prop e integração é responsabilidade do consumidor.

- [ ] CHK026 — Há requisito de fallback para o foco pós-vídeo quando o botão "Próximo módulo" existe no DOM mas está desabilitado (disabled)? [Cobertura, Spec §FR-010] [Gap] {auto}
  > Gap: FR-010 cobre apenas dois cenários (botão presente → foco nele; botão ausente → foco no `<video>`). Não define o caso onde `nextModuleButton` existe mas tem `disabled` ou `aria-disabled="true"`. Ação: definir comportamento (tratar disabled como ausente, ou focar mesmo assim) antes de implementar FR-010.

- [x] CHK027 — O requisito para o catalog variant de `trail-card.tsx` (sem `progressPercent`, sem dados de progresso) está coberto separadamente do content variant? [Cobertura, Spec §Scope, Plan §2] {auto}
  > Evidência: Plan §2 trata o catalog variant separadamente, com template `"Trilha: {name}, {statusLabel}, {moduleCount} módulos"` sem percentual (N/A para trilhas não iniciadas no catálogo).

## Cobertura de Edge Cases

- [x] CHK028 — Os edge cases de `progressPercent` em 0% e 100% estão cobertos para garantir `aria-label` bem formado? [Cobertura de Edge Cases, Spec §Edge Cases] {auto}
  > Evidência: Edge Case explícito na spec: "Progress bar aria-label must remain well-formed ('Progresso na trilha: 0%' and 'Progresso na trilha: 100%')".

- [x] CHK029 — O edge case de módulo com 0 aulas (divisão por zero potencial no cálculo de progresso) está coberto? [Cobertura de Edge Cases, Spec §Edge Cases] {auto}
  > Evidência: Edge Case explícito: "Module aria-label must not divide by zero; status defaults to 'Não iniciado' and position 'Módulo {n} de {total}'".

- [x] CHK030 — O edge case de nome de trilha com caracteres especiais no `aria-label` está endereçado? [Cobertura de Edge Cases, Spec §Edge Cases] {auto}
  > Evidência: Edge Case explícito: "`aria-label` interpolation must preserve the name verbatim (no HTML escaping artifacts)". Cobre aspas, acentos, símbolos.

- [ ] CHK031 — O edge case de `ModuleCompletionAnnounce` sendo montado APÓS o anúncio ser acionado (race condition de montagem) está coberto nos requisitos? [Cobertura de Edge Cases, Spec §FR-008] [Gap] {auto}
  > Gap: Plan §8 alerta que "O container `role="status"` deve estar presente no DOM **antes** de ser preenchido — renderizar no layout pai, não condicional". Porém nem a spec nem o plan definem requisito de teste que valide este comportamento de montagem. Ação: adicionar cenário de teste (unit test) para garantir que o componente está no DOM antes de receber `message` não vazia.

## Requisitos Não-Funcionais (A11y Específicos)

- [x] CHK032 — O requisito de zero layout shift (CLS=0) ao renderizar o `ModuleCompletionAnnounce` está definido? [NFR, Spec §FR-008, Plan §Tech Context] {auto}
  > Evidência: FR-008 exige `sr-only` (posição fixa, sem ocupar espaço visual) e plan define "Performance Goals: Zero layout shift (CLS=0)". `sr-only` do Tailwind satisfaz o requisito.

- [x] CHK033 — Os três hard gates a11y (focus-ring, contrast, motion-safe) têm critérios de aceite documentados como obrigatórios para CADA mudança de componente? [NFR, Spec §FR-012] {auto}
  > Evidência: FR-012 exige re-execução dos 3 gates após cada mudança. SC-005 cobre motion-safe especificamente. Os gates de focus-ring e contrast fazem parte do CI herdado do Epic 12.

- [x] CHK034 — O requisito de idioma PT-BR para todos os strings de `aria-label` está explicitado? [NFR, Spec §FR-009, §US1-US6] {auto}
  > Evidência: FR-009 especifica "in PT-BR" explicitamente. Todos os User Stories definem strings em PT-BR ("Módulo concluído!", "Vídeo: {título}", "Progresso na trilha: {x}%"). Consistente com CLAUDE.md regra de idioma para user-facing messages.

- [ ] CHK035 — Há requisito de teste de contraste específico para os textos de `aria-label` nos cards de trilha em modo escuro (dark mode)? [NFR, Spec §FR-012] [Gap] {humano}
  > Gap: FR-012 menciona o gate de `contrast` mas não define se o gate cobre modo escuro. O `aria-label` em si não é visível (portanto sem risco de contraste), mas o texto visível nos cards pode ter variação em dark mode. Decisão de produto: o gate de contraste existente já cobre dark mode ou é necessário gate adicional?

## Ambiguidades e Conflitos Identificados

- [ ] CHK040 — A ambiguidade entre `export const metadata` (Server Component) vs. `document.title` via `useEffect` (Client Component) para a page de trilhas está resolvida na spec? [Ambiguidade, Spec §FR-001, Plan §3] [Ambiguity] {humano}
  > Ambiguidade: Plan §3 identifica que a página atual é `'use client'` e o `metadata` export não funciona nela. FR-001 exige `<title>` e/ou `<h1>`. A solução (mover para Server Shell, usar `useEffect`, ou confiar apenas no `<h1>`) não está prescrita na spec. Decisão de produto: qual das abordagens é preferida para o título de documento?
