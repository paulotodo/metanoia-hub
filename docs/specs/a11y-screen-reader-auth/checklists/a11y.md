  > Evidência: AC-1 último bullet: "A `<nav>` só está presente quando há links de navegação (não obrigatória nas páginas públicas que não têm menu)" — critério claro e verificável.

- [x] CHK003 - Os requisitos de landmarks cobrem o layout de onboarding separadamente do layout público? [Completude, Spec §2.1, §3.2 LAC-01] {auto}
  > Evidência: Spec §2.1 tabela lista ambos os layouts separadamente. LAC-01 documenta explicitamente ambos com criticidade alta.

## 2. Completude de Requisitos de Formulários (ARIA)

- [x] CHK004 - É o requisito de `aria-labelledby` no formulário de login específico o suficiente (aponta ao h1 visível, não genérico)? [Clareza, Spec §4 AC-2] {auto}
  > Evidência: AC-2 especifica "o `<form>` tem `aria-labelledby` apontando para o `id` do `<h1>Entrar</h1>`". Plan §LAC-02 detalha o `id="login-form-heading"` específico.

- [x] CHK005 - São os requisitos do toggle de senha definidos com critérios mensuráveis (`aria-pressed`, SVG `aria-hidden`, `aria-label` dinâmico)? [Clareza, Spec §4 AC-3] {auto}
  > Evidência: AC-3 especifica exatamente: `aria-pressed="true"/"false"`, ícones SVG com `aria-hidden="true"`, e texto dos labels "Mostrar senha"/"Ocultar senha". Sem adjetivos vagos.

- [x] CHK006 - O requisito AC-3 cobre TODOS os formulários que têm toggle de senha (login, register, onboarding criar-conta)? [Cobertura, Spec §4 AC-3] {auto}
  > Evidência: AC-3 abre com "Dado que o toggle de senha está presente em login, register, onboarding criar-conta" — cobertura explícita de 3 contextos.

- [x] CHK007 - O requisito de `aria-live` no register especifica o tipo correto (polite vs assertive) e justifica a escolha? [Clareza, Spec §4 AC-4, Research §D4] {auto}
  > Evidência: AC-4 especifica `aria-live="polite"`. Research Decision 4 justifica: "interrupção assertiva não é desejada durante digitação". Tipo e justificativa presentes.

- [x] CHK008 - O AC-4 (register) cobre o estado de SUCESSO separadamente dos erros de validação? [Completude, Spec §4 AC-4] {auto}
  > Evidência: AC-4 penúltimo bullet: "o estado de sucesso ('Conta criada!') está em elemento com `role='status'`". Spec §3.1 confirma que `role="status"` já existe no register-form.tsx:90.

- [x] CHK009 - Os requisitos de recovery/nova-senha (AC-5) são simétricos com os do login, ou listam explicitamente o que deve ser implementado? [Consistência, Spec §4 AC-5] {auto}
  > Evidência: AC-5 especifica: landmarks (header/main/footer), `role="status"` para sucesso, `role="alert"` para erros. LAC-08 detalha o trabalho específico em `recovery-form.tsx`.

## 3. Cobertura de Cenários de Screen Reader

- [x] CHK010 - O requisito de gestão de foco no onboarding (AC-6) especifica PARA ONDE o foco deve ir (main? heading? elemento específico)? [Clareza, Spec §4 AC-6, Research §D5] {auto}
  > Evidência: AC-6 especifica "foco é movido para o `<main>` (ou heading principal)". Research Decision 5 confirma que `useFocusOnRouteChange` aplica fallback chain: seletor → `[data-autofocus]` → `h1` → `#conteudo`. Critério operacionalizável.

- [x] CHK011 - Os requisitos cobrem o anúncio de transições de etapa no onboarding (welcome→termos→criar-conta)? [Completude, Spec §4 AC-6] {auto}
  > Evidência: AC-6 segundo bullet: "transições de etapa têm anúncio polite via `AsyncAnnouncerProvider` ou `aria-live`". Plan §LAC-05 detalha a adição de `AsyncAnnouncerProvider`.

- [x] CHK012 - O requisito de `lang` inline (AC-7) fornece uma lista fechada de termos elegíveis ou critério de seleção verificável? [Clareza, Spec §Clarifications C1, Research §D6] {auto}
  > Evidência: Clarification C1 (dec-008) define lista fechada: Dashboard, Radar, VoiceOver, NVDA, JAWS, check-in, login, onboarding. Research D6 tabela completa com justificativa por termo.

- [x] CHK013 - O AC-7 distingue entre termos em texto renderizado (JSX) e comentários/variáveis (sem `lang`)? [Clareza, Spec §Clarifications C1] {auto}
  > Evidência: C1 especifica "apenas em texto renderizado de telas públicas + packages/ui. Não aplicar em comentários ou variáveis."

- [x] CHK014 - Os requisitos cobrem o comportamento esperado quando o screen reader encontra os landmarks (anúncio de região)? [Cobertura, Spec §4 AC-1] {auto}
  > Evidência: AC-1 especifica que "a estrutura de landmarks inclui" os elementos — o anúncio por região é comportamento implícito do landmark (não precisa ser especificado no HTML; é responsabilidade do AT). Requisito é da estrutura, não do comportamento do AT. PASS — escopo correto.

## 6. Cobertura de Edge Cases

- [x] CHK021 - O requisito de `aria-pressed` no toggle cobre o estado inicial (quando a página carrega com senha oculta)? [Edge Case, Spec §4 AC-3] {auto}
  > Evidência: AC-3 especifica `aria-pressed="true"` quando visível e `aria-pressed="false"` quando oculta — cobre estado inicial implicitamente (`false` = senha oculta por default).

- [x] CHK022 - Os requisitos cobrem o comportamento quando o formulário é submetido e volta ao estado inicial (reset de foco)? [Edge Case, Spec §3.1] {auto}
  > Evidência: Spec §3.1 documenta que `scrollToFirstError` + `role="alert"` já estão implementados para o caso de submissão com erro (login-form.tsx:155). O estado de sucesso (redirecionamento) não precisa de foco — PASS.

- [x] CHK023 - São os requisitos de lang inline aplicados também a termos que aparecem via `pt-BR.json` (não apenas hardcoded em JSX)? [Cobertura, Spec §Clarifications C1, Research §D6] {auto}
  > Evidência: Research §D6 nota: "os termos VoiceOver/NVDA/JAWS aparecem apenas no roteiro manual (markdown), não em componentes React. No HTML renderizado ao usuário, os termos relevantes são 'login', 'onboarding' e 'Dashboard'." Não há termos elegíveis em `pt-BR.json` — PASS.

- [ ] CHK024 - Há requisito definido para o caso em que o FocusManager do onboarding não encontra `h1` nem `#conteudo`? [Edge Case, Spec §4 AC-6] {humano}
  > O `useFocusOnRouteChange` tem fallback chain (D5), mas se nenhum elemento for encontrado, o hook faz `fail-silent` (retorna `null`). O requisito AC-6 não especifica o comportamento de fallback quando o foco não pode ser movido. Decisão do PO: é aceitável o fail-silent ou deve-se documentar um fallback visível?

- [x] CHK025 - O requisito de `role="status"` na recovery cobre TAMBÉM o estado de loading (antes do sent)? [Cobertura, Spec §4 AC-5, Spec §3.2 LAC-08] {auto}
  > Evidência: LAC-08 especifica "estado 'sent' falta `role='status'`". O estado loading (formState='sending') tem loading visual mas não é um anúncio de status — o loading é transitório e não requer `role="status"`. Plan §LAC-08 confirma escopo no estado de confirmação. PASS.

## 8. Requisitos Não-Funcionais

- [x] CHK030 - O requisito de zero novas violações axe-core (SC-1) é verificável automaticamente pelo CI existente? [Mensurabilidade, Spec §5 SC-1] {auto}
  > Evidência: SC-1: "páginas `/login`, `/register`, `/recuperar-senha` já estão em modo `hard` no `a11y-pages.json`... O CI bloqueia automaticamente." Spec §8 lista `bash scripts/check-focus-ring-variants.sh --ci` etc. como gates.

- [x] CHK031 - O limite honesto sobre teste manual com screen readers é documentado de forma que a story não possa ser marcada DONE sem ele? [Mensurabilidade, Spec §6] {auto}
  > Evidência: Spec §6 "A story só pode ser marcada como DONE após um humano executar o roteiro e documentar os resultados." AC-9 faz parte dos ACs formais (não opcional).

- [x] CHK032 - O requisito SC-2 (sem alteração de ratchet) é específico o suficiente para evitar adição acidental de páginas ao `a11y-pages.json`? [Clareza, Spec §5 SC-2] {auto}
  > Evidência: SC-2: "NÃO adicionar páginas ao `a11y-pages.json` (promoção de baseline→hard é escopo de 15.2/15.4)." SC-3: "Páginas `/convite/[token]/*` não estão no `a11y-pages.json` e NÃO devem ser adicionadas nesta story." Dupla camada de especificidade.

- [x] CHK033 - Os validation gates do spec §8 cobrem tanto regressão funcional (testes) quanto regressão a11y (scripts hard)? [Completude, Spec §8] {auto}
  > Evidência: Spec §8 lista: (1) lint, (2) testes unitários web, (3) build web, (4) 3 scripts hard a11y, (5) condicional packages/ui. Cobertura: funcional + a11y + build.

- [x] CHK036 - A decisão SC-6 (sem tenant name dinâmico no `<title>`) tem justificativa técnica suficiente? [Clareza, Spec §5 SC-6] {auto}

Implementação dinâmica... é escopo de infraestrutura de tenant-branding (feature `branding-tenant`)." Justificativa técnica clara com referência à feature futura.
