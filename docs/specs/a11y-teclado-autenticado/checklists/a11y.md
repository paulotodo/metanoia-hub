# A11y Checklist: Navegação por Teclado — Fluxos Autenticados

**Purpose**: Quality gate de REQUISITOS — valida completude, clareza, consistência e
mensurabilidade dos requisitos de acessibilidade por teclado para os 7 fluxos autenticados
da Story 12.2 (Epic 12). Conceito: "unit tests for English".
**Created**: 2026-06-16
**Feature**: [spec.md](../spec.md) | [plan.md](../plan.md)
**Domínio**: a11y (WCAG 2.1/2.2 AA — navegação por teclado)
**Fluxos cobertos**: Dashboard (US1), Foco pós-login (US2), CRUD Grupos (US3),
Builder Trilhas (US4), Catálogo/Busca (US5), Config Tenant (US6), Gestão Planos (US7)

## 2. Clareza e Especificidade dos Requisitos

- [ ] CHK007 - "Primeiro elemento interativo significativo" (FR-006) está operacionalmente definido na spec? [Clareza, Spec §FR-006, Gap] {auto}
  > [Gap] FR-006 usa o termo sem defini-lo: "primeiro elemento interativo significativo da página de destino". A definição operacional está no plan (Decision 2: busca em `#conteudo`, prioridade `[data-autofocus]` → `h1` → primeiro interativo), mas a spec não a incorpora. Requisito na spec é incompleto sem essa definição — comportamento esperado depende do leitor conhecer o plan.

- [x] CHK008 - O comportamento de wrap circular da sidebar (Arrow Down no último → primeiro) está especificado? [Clareza, Spec §CL-003, Plan §Decision 3] {auto}
  > Evidência: CL-003 (spec §Clarifications) afirma "Arrow Up/Down move foco entre itens sem sair do grupo" com roving tabindex. Plan Decision 3 especifica explicitamente "Arrow Down: próximo item (circular: último → primeiro)". A clarification absorve o comportamento; está coberto.

- [ ] CHK009 - FR-004 ("menu lateral DEVE ser navegável com teclas de seta entre seus itens") especifica o comportamento de wrap e de Home/End? [Clareza, Spec §FR-004, Ambiguity] {auto}
  > [Ambiguity] FR-004 não menciona wrap circular nem suporte a Home/End. CL-003 e plan Decision 3 especificam ambos, mas a discrepância entre a FR e a clarification cria ambiguidade: a FR é o contrato testável; a clarification é onde o comportamento está detalhado. Qualquer teste que se baseie apenas em FR-004 vai ficar subspecificado.

- [x] CHK010 - US4 Acceptance Scenario 4 ("experiência equivalente ao mouse") tem critério mensurável? [Clareza, Spec §US4, SC-003] {auto}
  > Evidência parcial: SC-003 quantifica a reordenação como "N×2 interações (uma tecla por direção)", convertendo "equivalente" em métrica objetiva. O acceptance scenario 4 em si é vago, mas o success criterion associado resolve a mensurabilidade. Aceitável: SC-003 é o contrato testável.

- [x] CHK011 - "Foco preso" (US1 Scenario 4) está definido de forma verificável? [Clareza, Spec §US1, SC-007] {auto}
  > Evidência: SC-007 define "focus trap funcional: Tab não deixa o foco escapar do diálogo; Escape fecha e restaura o foco ao elemento de origem." Objetivamente verificável por E2E (tab count dentro do dialog). US1 Scenario 4 cobre foco preso FORA de diálogos — coberto por axe-core violation `keyboard-trap`.

- [x] CHK012 - As mensagens PT-BR para `aria-live` estão especificadas com conteúdo exato ou padrão de template? [Clareza, Spec §CL-005, Plan §1.4] {auto}
  > Evidência: Plan §1.4 lista 3 templates: busca ("N resultados encontrados para [termo]"), config ("Configurações salvas com sucesso."), reordenação ("[Item] movido para a posição [N]."). Conteúdo suficientemente especificado.

- [ ] CHK013 - FR-027 (cross-browser manual) define quem é responsável pela execução e em qual momento do ciclo de entrega? [Clareza, Spec §FR-027, Gap] {auto}
  > [Gap] FR-027 define "o quê" (3 browsers, checklist por fluxo, classificação por severidade) mas não define "quem" executa nem "quando" (antes do merge? antes do release?). Sem esse escopo operacional, o requisito pode não ser executado ou pode bloquear indefinidamente.

## 3. Consistência entre Requisitos

- [x] CHK014 - CL-005 (foco permanece na origem após async) é consistente com FR-013 (foco permanece no botão após reordenação)? [Consistência, Spec §CL-005, FR-013] {auto}
  > Evidência: Consistentes. CL-005 define o padrão geral; FR-013 é uma aplicação específica. Sem conflito.

- [x] CHK015 - CL-002 (usar Radix Dialog para focus trap) é consistente com FR-009 (focus trap em diálogos de grupos)? [Consistência, Spec §CL-002, FR-009] {auto}
  > Evidência: FR-009 define o comportamento; CL-002 define o mecanismo. Complementares e consistentes — Radix satisfaz FR-009 nativamente.

- [x] CHK016 - O escopo de CL-002 (Radix Dialog) exclui o OnboardingWizard de forma documentada e justificada? [Consistência, Spec §CL-002, Plan §Decision 5] {auto}
  > Evidência: Plan Decision 5 documenta a exclusão com justificativa técnica: OnboardingWizard usa `role="dialog"` customizado no grupo `(onboarding)`, fora do escopo `(authenticated)`.

- [x] CHK017 - FR-012 (botões sempre visíveis) é consistente com CL-004 e não conflita com requisitos de UI anteriores? [Consistência, Spec §FR-012, CL-004] {auto}
  > Evidência: CL-004 documenta a decisão do operador como requisito explícito. Sem FR de UI anterior que contrarie. Plan §1.5 implementa `disabled`+`aria-disabled` para estados de borda.

- [ ] CHK018 - SC-005 (E2E no CI) e FR-027 (cross-browser manual) são consistentes quanto ao escopo automatizado vs. manual? [Consistência, Spec §SC-005, FR-027, Ambiguity] {auto}
  > [Ambiguity] SC-005 restringe CI ao Chromium; FR-027 exige Firefox e Safari manualmente. A decisão está documentada no plan (§Verificação Cross-Browser), mas a spec não declara explicitamente que Firefox/Safari são EXCLUSIVAMENTE manuais. Um leitor da spec isolada pode interpretar que o CI deveria cobrir os 3 browsers.

## 4. Qualidade dos Critérios de Aceite

- [x] CHK019 - SC-001 ("100% dos 7 fluxos") é objetivamente verificável com os testes definidos? [Mensurabilidade, Spec §SC-001, FR-025] {auto}
  > Evidência: FR-025 exige 1 E2E por fluxo; plan lista 7 arquivos E2E correspondentes. SC-001 verificável: 7 specs E2E passando = 100% cobertos.

- [x] CHK020 - SC-002 ("foco em elemento interativo em 100% dos casos testados") é objetivamente verificável? [Mensurabilidade, Spec §SC-002] {auto}
  > Evidência: Plan §US2 define `document.activeElement !== document.body` como critério de pass — objetivamente verificável por Playwright.

- [x] CHK021 - SC-003 ("N×2 interações para reordenação") é objetivamente verificável sem ambiguidade sobre "interação"? [Mensurabilidade, Spec §SC-003] {auto}
  > Evidência: Contexto define "uma tecla por direção" = 1 keypress = 1 interação. Verificável por contagem de eventos de teclado em E2E.

- [x] CHK022 - SC-004 ("zero problemas bloqueadores") tem definição de "bloqueador" explicitada? [Mensurabilidade, Spec §SC-004, FR-002] {auto}
  > Evidência: FR-002 define "bloqueador: impede completar tarefa principal sem mouse". Definição presente e operacional.

- [x] CHK023 - SC-006 ("checklist cross-browser sem bloqueadores") tem definição de "bloqueador" consistente com FR-002? [Mensurabilidade, Spec §SC-006, FR-002] {auto}
  > Evidência: FR-002 define bloqueador; SC-006 reutiliza o mesmo critério. Consistente.

- [ ] CHK024 - Existe critério de aceite para a latência do `useFocusOnRouteChange` (< 16ms mencionado no plan)? [Mensurabilidade, Spec §FR-006, Plan §Performance Goals, Gap] {auto}
  > [Gap] O target "foco programático em < 16ms (1 frame) após mudança de rota" está no plan (§Performance Goals) mas não há FR ou SC correspondente na spec. Se obrigatório, deve ser promovido para a spec como SC ou NFR mensurável; caso contrário, rotulá-lo como guideline no plan.

## 5. Cobertura de Cenários por Fluxo

- [x] CHK025 - US1 (Dashboard) cobre os 3 sub-contextos de experiência (Consumo, Gestão, Admin)? [Cobertura, Spec §US1, FR-005] {auto}
  > Evidência: US1 Acceptance Scenario 3 testa o seletor de experiência. FR-005 cobre o seletor. Cobertura dos 3 papéis implicada pelo seletor de experiência.

- [x] CHK026 - US2 (foco pós-login) cobre re-login após expiração de sessão? [Cobertura, Spec §US2] {auto}
  > Evidência: US2 Acceptance Scenario 2 cobre explicitamente "expiração de sessão seguida de re-login".

- [x] CHK027 - US3 (CRUD grupos) cobre o ciclo completo: criar, editar, excluir e convidar membros via CSV? [Cobertura, Spec §US3, FR-008..011] {auto}
  > Evidência: US3 acceptance scenarios 1..4 cobrem formulário de criação (Tab), diálogo de exclusão (focus trap + Escape), upload CSV (FR-010), e foco retorno após ação (FR-011).

- [x] CHK028 - US4 (builder trilhas) cobre o estado de borda: botão desabilitado no primeiro/último item? [Cobertura, Spec §CL-004, Plan §1.5] {auto}
  > Evidência: CL-004 especifica `disabled`+`aria-disabled="true"` para o primeiro e último item. Plan §US4 cenários inclui testes de `disabled` como itens unitários.

- [x] CHK029 - US5 (catálogo) cobre paginação além de busca e filtros? [Cobertura, Spec §US5, FR-018] {auto}
  > Evidência: US5 Acceptance Scenario 4 cobre paginação; FR-018 é requisito explícito para controles de paginação.

- [x] CHK030 - US6 (config tenant) cobre upload de arquivo (logo) além de campos de texto e seletor de cor? [Cobertura, Spec §US6, FR-021] {auto}
  > Evidência: US6 Acceptance Scenario 3 cobre upload de logo; FR-021 é requisito explícito. Plan §US6 cenários inclui "Enter abre diálogo de arquivo".

- [x] CHK031 - US7 (gestão planos) cobre o fluxo completo de upgrade incluindo passos de confirmação/pagamento? [Cobertura, Spec §US7, FR-024] {auto}
  > Evidência: US7 Acceptance Scenario 4 cobre "todos os passos do fluxo (confirmação, pagamento se aplicável)". "Se aplicável" é escopo condicional aceitável dado que pagamento pode não estar disponível em staging.

## 6. Cobertura de Edge Cases

- [x] CHK032 - O edge case de modal aberto via teclado → Escape → foco retorna ao trigger está especificado? [Edge Cases, Spec §Edge Cases, FR-009] {auto}
  > Evidência: Seção "Edge Cases" da spec cobre explicitamente este caso. FR-009 formaliza o requisito. CL-002 (Radix Dialog) provê o mecanismo nativamente.

- [x] CHK033 - O edge case de conteúdo dinâmico SPA (resultados de busca carregados) está endereçado? [Edge Cases, Spec §Edge Cases, CL-005] {auto}
  > Evidência: Seção "Edge Cases" menciona o cenário; CL-005 define que o foco permanece no elemento de origem e aria-live anuncia a contagem — sem mover o foco para os resultados.

- [x] CHK034 - O edge case de "último item de lista navegável" (foco não deve vazar) está coberto? [Edge Cases, Spec §Edge Cases, CL-003] {auto}
  > Evidência: Seção "Edge Cases" descreve o cenário. CL-003 + roving tabindex: Tab sai do grupo inteiro (tabIndex=-1 nos não-ativos), evitando o vazamento. Plan Decision 3 documenta o comportamento.

- [x] CHK035 - O edge case de operação assíncrona com anúncio de status está coberto para US1, US5 e US6? [Edge Cases, Spec §CL-005, Edge Cases] {auto}
  > Evidência: Seção "Edge Cases" cobre operações assíncronas. CL-005 define padrão uniforme. Plan §1.4 lista as 3 mensagens PT-BR de anúncio por contexto.

- [ ] CHK036 - Existe cobertura de requisito para o caso de rota profunda com parâmetros dinâmicos (ex: `/groups/[id]`) no foco pós-redirect? [Edge Cases, Spec §US2, FR-007, Ambiguity] {auto}
  > [Ambiguity] FR-007 afirma "a lógica cobre rotas diretas e rotas profundas igualmente". Plan Decision 2 define o seletor via `#conteudo`, mas não especifica como o hook lida com slugs dinâmicos. A spec não documenta que `usePathname()` expõe rotas dinâmicas resolvidas — é uma premissa de implementação não validada na spec.

- [x] CHK037 - O comportamento de focus trap em diálogos de confirmação de ações destrutivas está especificado separadamente de outros diálogos? [Edge Cases, Spec §FR-009, SC-007, Edge Cases] {auto}
  > Evidência: Seção "Edge Cases" menciona diálogos de ações destrutivas especificamente. FR-009 e SC-007 cobrem focus trap. CL-002 exclui explicitamente o OnboardingWizard (que não é destrutivo).

## 7. Requisitos Não-Funcionais (WCAG / A11y)

- [x] CHK038 - O padrão WCAG 2.1/2.2 AA é referenciado como nível de conformidade alvo? [NFR, Spec §Constitution Check, Plan §Technical Context] {auto}
  > Evidência: Plan §Technical Context afirma "WCAG AA como requisito" (princípio VI da constitution). A spec não declara WCAG AA explicitamente nos §Requirements, mas plan e constitution compensam. Satisfatório.

- [x] CHK039 - O padrão WAI-ARIA APG é referenciado como base para os padrões de interação (roving tabindex, focus trap)? [NFR, Spec §CL-003, CL-005] {auto}
  > Evidência: CL-003 cita "WAI-ARIA APG (Listbox Pattern)" para roving tabindex. CL-005 cita "Padrão WAI-ARIA APG explícito" para o comportamento de foco + aria-live.

- [x] CHK040 - As ferramentas de verificação automatizada de a11y (axe-core, jest-axe) estão especificadas como requisito? [NFR, Spec §FR-025, FR-026, Plan §Technical Context] {auto}
  > Evidência: FR-025 e FR-026 exigem testes E2E e unit com ferramentas de a11y. Plan §Technical Context lista `@axe-core/playwright` e `jest-axe` como dependências primárias já instaladas.

- [ ] CHK041 - Existe requisito não-funcional para suporte a leitores de tela (NVDA, VoiceOver) além da navegação por teclado puro? [NFR, Gap] {humano}
  > A spec cobre navegação por teclado e aria-live, mas não declara se a story deve ser testada com leitores de tela reais (NVDA, VoiceOver). Leitor de tela é critério adicional de acessibilidade — decisão de escopo para o dono do produto.

- [x] CHK042 - O requisito de `aria-label` descritivo (incluindo título do item) para os botões de reordenação está especificado? [NFR, Spec §CL-004, FR-012] {auto}
  > Evidência: CL-004 especifica explicitamente o template `aria-label={Mover "${titulo}" para cima}`. FR-012 requer "rótulos descritivos". Plan §1.5 detalha o contrato de props.
